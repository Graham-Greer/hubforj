# Repairing a signup with no saved operation

Scope: STOP-04, a founder-operated development/limited-release procedure. Tool defaults to dry-run. It is not a public endpoint and does not create hubs, change passwords, enable accounts, send messages or start checkout. [Closure audit](product-site-stopping-point-audit.md).

1. Confirm the affected account ID with the signed-in owner. Independently check the current Firebase UID and verified email. If verification was never delivered, use the configured verification process first; never mark an unfamiliar identity verified just to bypass this tool.
2. Stop other signup/administrative writers for this affected account during the repair. Inspect existing hubs (including legacy hubs), ownership links and provisioning operations. An existing saved operation uses normal recovery; do not remove it. If a legacy hub already exists, reconcile its ownership separately rather than create another hub. The tool also rejects a hub with the same contact email, but this bounded check cannot replace review of unusual legacy records.
3. Have the owner confirm their community name/address and selected tier. Create a temporary input JSON outside version control with `accountId`, `authUid`, `tier` (`free`, `starter`, `growth`), `currency` (`GBP`), and `payload`. Payload contains the owner-confirmed canonical non-secret provisioning fields: `name`, `slug`, `contactEmail`, `customDomain` (empty), `template`, `theme`, `country`, `timezone`, `locale`, `defaultCurrency`, `description`, and **Free/active/product_site** as `packageTier`/`packageStatus`/`packageSource`. Never include passwords, tokens, service credentials or arbitrary entitlement overrides.
4. From `apps/product-site`, using Node 24 and the intended project's credentials, run `node --env-file=.env.local scripts/reconcile-commercial-signup.mjs /path/to/input.json`. This is read-only and checks identity/status/conflicts; it does not imply the payload has already passed the transactional creation checks. Confirm the project externally and review the returned IDs before applying.
5. Run the same command with `--apply` only for that reviewed case. Existing UID binding cannot be replaced. The standard transactional operation writer validates canonical intent and rechecks active status, identity and ownership. If identity binding succeeded but operation persistence failed, inspect the failure and repeat the review; that partial binding is safe to retry. Never delete records blindly to make a retry pass.
6. Ask the owner to sign in through `/signup/recover`. Normal authenticated recovery creates at most one hub using the saved operation key. Check one owner link, one hub count, matching address claim and completed operation; paid choices remain checkout intent until paid through the usual route.
7. Record only IDs, outcome and verification in the support/audit record; remove the temporary input according to its handling needs. Restore affected writers after verification.

The dedicated emulator regression covers unverified-identity rejection, read-only review, binding an unbound matching verified identity, operation persistence, existing-operation rejection and subsequent ordinary recovery. No real-project repair was performed during closure. For already linked/ambiguous legacy hubs, stop and investigate; this procedure is intentionally not a general account-merging tool.
